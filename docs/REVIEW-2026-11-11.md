## Findings, ordered by practical priority

### 1. Pending saves can be skipped on sign-out — high priority, source-based finding

`queueCloud()` schedules uploads after 1.2 seconds. `signOut()` calls `pushCloud()` only when `CLOUD.failed` or `CLOUD.busy` is true. A freshly queued change can satisfy neither condition, letting sign-out clear local state before upload. Also, `pushCloud()` returns immediately if another upload is busy, so awaiting it does not guarantee that in-flight work has settled.

Evidence: `queueCloud`, `pushCloud`, `signOut` (~1682-1700 and ~1878). No real-account reproduction was performed. Follow-up: a drain/flush operation that awaits pending/in-flight work, tested with synthetic queued edits, completed logs, failures, and account switching. Until addressed, wait for saving to finish before signing out.

### 2. Multi-device sync can overwrite edits or revive deleted logs — high priority, design limit

State is one JSON document selected by client timestamps. Uploads lack conditional version checks, and state/log operations are separate requests. `onSignedIn()` unions remote/cached logs by ID with no deletion tombstones. A stale device can reintroduce a deleted log; simultaneous setup/plan edits do not merge field by field.

Evidence: `onSignedIn`, `pushCloud`, `pullCloud`. This follows from the code; a two-device race was not exercised live. Follow-up needs conflict/deletion semantics, version checks, and an isolated multi-client test. Single-device saving cannot validate it.

### 3. Offline startup is not guaranteed — medium priority, confirmed repository limitation

The manifest supports Home Screen presentation, but no service worker/offline app-shell cache exists. SDK/fonts are remote. Local data/reconnect support can preserve work in an already-loaded page; it does not guarantee opening a closed app offline. If the SDK fails to load, `sb` becomes null and the app falls back to local behavior instead of cloud features.

Evidence: manifest, external script/font tags, `sb` initialization, absence of service-worker files/registration. Offline promises need airplane-mode/closed-app testing and an approved caching design.

### 4. Plan update acknowledgement precedes durable saving — medium priority, source-based concern

`applyPlanUpdates()` modifies memory, marks remote updates applied, then calls `save()` for persistence. A crash/storage failure between those steps can consume the update before the new plan is durably saved. Cloud upload is another separate step.

Evidence: `applyPlanUpdates` (~1714). No fault-injection reproduction was run. Follow-up should make application retryable/idempotent and test interrupted acknowledgement/persistence. Reordering alone needs consideration of duplicates and offline recovery.

### 5. Unit changes reinterpret stored numbers — medium priority, confirmed behavior

`setunits` changes `state.settings.units` and asks the person to re-enter weights. It does not convert progression, historical entries, body weight, or weigh-ins. History uses the current unit label. Historical values can therefore become misleading after a switch.

Evidence: `setunits` (~4229), `fmtW`, history chart, `suggestW`/`bwLb`. Documented in the guide. Conversion needs a schema/migration plan and product approval, not just relabeling.

### 6. Permissions require grant review; some broad grants merit follow-up — medium priority, metadata finding

All public tables had RLS. Member isolation/role checks exist, and profile approval/disable fields are protected by column grants. Feedback updates allow only read/done fields; invite updates allow cancellation. Row policies alone give an incomplete picture.

`plan_updates` grants authenticated UPDATE on every column while recipient policy restricts row ownership. A recipient can potentially rewrite more than `applied_at` on their own rows. This is not demonstrated cross-account access, but exceeds the UI's write needs. Consider column-limiting updates and test realistic roles in an isolated database.

### 7. Database/dependency reproducibility needs stronger records — medium priority

Seven remote migrations exist, but their SQL files are absent from Git. A clean checkout cannot independently recreate database/Auth configuration. The SDK URL follows the v2 major, so behavior can change without a repo diff. No checked-in regression runner or CI application checks exist.

Follow-up: recover/version migration history, document nonsecret Auth/redirect settings, pin the production SDK through an approved change, and add focused persistence/role tests before expanding beta. These changes were not implemented during this task.

### 8. Timing text and privacy wording need owner review — lower priority

Today states a fixed five-minute warm-up and ten-minute cool-down, while previews use dynamic budgets; the sample preview showed six minutes each. In the randomized VM smoke run, 10 of 784 sessions exceeded the selected time by more than one minute, with a maximum two-minute excess. This sample is not a universal bound.

The privacy page does not explicitly explain feedback/device context and beta invite/account-management records. Retained app feedback loses profile/workout references on deletion, but free-text message/screen/device fields can still identify someone. Privacy/deletion promises should reflect actual retention. Legal/product wording was not changed.
